> 이 계획은 코드·출력물·외부 사실을 전부 실측 조사한 뒤 쓴 것이다(근거는 각 항목에 파일:줄).

## 0. 한 줄 요약

**이미 생성된 14부의 TTS·이미지·비디오 파일을 "통합대본" 새 작업에 복사·연결해 주는 「📥 자산 이어받기」 기능 하나만 만들면, 나머지(빌드·게이트·타임스탬프·.vrew)는 기존 코드가 무수정으로 다 한다.** .vrew 파일을 자르거나 합치는 수술은 하지 않는다.

## 1. 배경 (왜 이 기능인가)

- 고전서재 = 고전 완역 오디오북 채널. 빨간머리앤을 **14부**(각 47~73분)로 만들었고, 이를 **통합본 3개**(1~5부 / 6~10부 / 11~14부)로도 낸다.
- **통합본이 채널의 주력이다** — 채널 지침 `D:\## 아도나이로이\01_고전\02_고전서재\지침\config.md` §통합본 트랙에 실측으로 확정돼 있다(상위 성과 규격 = 4~5시간, 현대지성 5시간 통합본 171k 조회 실증).
- 같은 config §이어붙이기 규격에 **어느 섹션을 잘라내는지 규격표**가 이미 있다(아래 §4-1).
- 통합본 1·2·3의 **「문」(새 인트로)·「맺음」(새 아웃트로)은 이미 대본·.vrew까지 생성 완료** (`대본\_통합본\`, 출력폴더에 실재).
- 남은 문제 = **본체(각 부의 낭독 구간)를 재생성 비용 없이 이어 붙이는 것.** 지금까지의 계획은 "Vrew에서 수동 클립 복붙"이었는데(그래서 config에 자수 비율로 컷 시각을 추정하는 절차까지 있다), 이걸 Priming이 대신한다.

### 1-C. 🔴 이미지와 TTS 는 사정이 다르다 (실측 — 설계의 핵심)

같은 "콘텐츠 주소 캐시" 구조인데 결과가 정반대다. 이것이 이어받기 기능이 **무엇을 위한 것인지**를 정한다.

| | 캐시 적중 실측 | 결론 |
|---|---|---|
| **이미지**(media-cache) | 기존 프롬프트 **40/40 = 100%** (styleId `user_1787204022733_dnbi` + engine `comfy::…image_krea2_turbo_t2i (2).json` + `16:9`) | **이어받기 없이도 앱이 자동 복원한다.** prefillImageCache 가 「🖼 이미지」·「만들기」 때 캐시에서 꺼내 media-1 로 복사 |
| **TTS**(tts-cache) | 1부 **11/120(9%)** · 2부 **1/120(0.8%)** — 배속 1.15 로 조회하면 **0** | **캐시로는 안 된다.** v0.3.29 가 키에 `rn`(refName)을 추가해 8/21 이전(=14부 생성 시점) 캐시가 자연 무효화됐다(F6 확인) |

- 조회 조건(실측에 쓴 값): 프리셋 `06_고전서재` = engine omnivoice · ref `srv:#01_득수_noBreath` · seed 40469 · cfg 2 · it 32 · lang ko · 배속 1.
- 🔑 **따라서 이어받기 기능의 본질은 TTS 다.** 이미지·비디오도 같은 코드로 연결하되(캐시가 못 잡는 경우의 안전망), 없으면 안 되는 것은 **문장별 `ttsAudioPath` + `ttsDurationSec` 주입**이다. 기존 음성 파일 12,304개는 각 부 `tts-1/`에 그대로 있고 통합대본과 4,182/4,182 매칭된다 — **파일은 있는데 앱이 그것을 가리킬 방법이 없는 것**이 유일한 문제다.
- ⚠ 대안으로 검토했다가 기각: 기존 tts 파일을 TTS 캐시에 역등록(`TtsCache.put`)하면 즉시 재사용되지만, **「🗑 TTS 삭제」 한 번에 clearAll 로 전부 사라지는 저장소**라 정본이 될 수 없다(main.js:1276). 로이 결정 = **정식 기능으로 간다.**

### 부분 합성 상태 처리 (구현 시 반영 필수)
2026-08-22 20:37에 이어받기 없이 「만들기」를 눌러 **통합본1 출력폴더에 새로 합성된 TTS 16개(`tts-1/1~16`)와 스냅샷이 이미 생성돼 있다.** 이어받기 구현은 이 상태를 반드시 덮어써야 한다:
- `copyIntoWorkdirs`는 **대상 파일이 이미 있어도 무조건 복사(덮어쓰기)** 한다. "있으면 스킵"으로 만들면 그 16문장은 영원히 새 음성을 쓴다(F1 때문에 이후 fillTts도 건너뛴다).
- 또는 이어받기 실행 전에 그 출력폴더의 `tts-1`·`media-1`과 스냅샷을 지우고 시작하는 옵션(`clean:true`)을 둔다.

## 3. 아키텍처 결정

### 채택 — B안: 통합대본(완전한 .md) + 「자산 이어받기」(텍스트 매칭·복사) + 기존 빌드 경로 그대로

```
[아도나이로이 세션]  통합대본.md 생성 (문 + 각 부의 남길 섹션 verbatim + 맺음)
                     + 각 부의 자산출처 메타 줄 삽입
        ↓
[Priming 신기능]     대본 열기 → 자산출처 감지 → 소스 출력폴더에서
                     문장(텍스트 매칭)·그룹(프롬프트 매칭)별 자산을
                     통합 출력폴더 tts-1/·media-1/로 복사 + 경로·duration 주입
                     → 스냅샷 저장 → 매칭 리포트
        ↓
[기존 코드 무수정]   🎤 TTS(미매칭분만 합성, F1) → 🖼/🎬(미매칭분만, F2)
                     → ⏱ 타임스탬프 → 💾 .vrew (게이트 F3 통과, 한 번에 빌드 F12·F15)
```

### 기각한 대안과 이유

- **A. .vrew zip 수술(로이 최초 아이디어 — 14개 .vrew에서 낭독 클립을 잘라 이어붙이기)**: 방향(재사용)은 맞지만 수단이 손해다. files[]↔tracks↔assets↔clips id 전면 재매핑 + zIndex 재발번호 + AI고지 절대시각 재계산 + 40bit id 충돌 검사(F14)를 전부 손으로 재구현해야 하는데, **빌더는 어차피 문장 배열을 통째로 받아 이 모든 불변식을 공짜로 보장**한다(F12·F15). 자산(오디오·이미지)은 .vrew 안에도 있지만 **디스크의 원본 폴더에 더 깨끗한 형태로 있다** — zip에서 꺼낼 이유가 없다. Vrew를 거쳐 재저장된 파일은 스키마가 다를 수 있어(실사용 Vrew는 4.2.x 추정) 파싱 자체가 미검증 영역.
- **C. 파서 확장(`## [가져오기]` 지시어)**: 재파싱 3경로(resplit·재시작 복원·대본수정)에서 전개 로직이 파서 안에 있어야 하는 부담 + 순환 참조 + 문장 id 충돌 계열 함정이 많고, 결정적으로 **TTS 캐시가 무효(F6)라 "지시어만으로 비용 0"이 성립하지 않는다** — 어차피 자산 복사 단계가 필요하다. 그렇다면 파서는 건드리지 않는 편이 싸고 안전하다.
- **D. MP4 수준 ffmpeg concat**: 비용은 가장 싸지만 컷 정밀도(키프레임)·인코딩 일치 문제가 있고, .vrew가 나오지 않아 채널의 기존 마무리 흐름(자막 스타일·Vrew 내보내기)과 갈라진다. **Vrew가 통합본 규모를 못 열 때의 폴백**으로 보류(§7).

## 4. 입력 계약 — 통합대본 .md

### 4-1. 본문 구성 (아도나이로이 세션 담당 — config §이어붙이기 규격 그대로)

```
# 빨간머리앤 통합본 1 · 브라이트리버 역에서 초록 지붕 집까지   ← 새 H1
> (채널 메타 — 기존 롱폼과 동일)
> 📥 자산출처: <문.md 절대경로> | <문 출력폴더 절대경로>
> 📥 자산출처: <1부.md 절대경로> | <1부 출력폴더 절대경로>
> 📥 자산출처: <2부.md 절대경로> | <2부 출력폴더 절대경로>
  ... (순서대로 — 매칭은 이 순서를 따른다)

[문 대본의 본문 섹션들 — 글자 그대로]
[1부: 도입부·지난 이야기 제외, 여는 이야기~마무리(끝 2문장 잘라낸)까지 — 글자 그대로]
[2부: 같은 규칙] ... [5부: 같은 규칙]
[맺음 대본의 본문 섹션들 — 글자 그대로]
```

- 섹션 잘라내기 규격은 config §이어붙이기 규격 표가 정본: `도입부`⛔ `지난 이야기`⛔ / `여는 이야기`·`읽기 전에`·`오늘 읽을 대목`·`장 사이`·`낭독을 마치며`✅ / `마무리`는 **끝 2문장(댓글 요청 + "N번째 이야기에서 뵙겠습니다")만 제거**(마지막 부 포함 — 맺음이 끝인사를 대신).
- 🔴 **남기는 본문은 원본에서 글자 그대로 복사한다.** 한 글자라도 다르면 그 문장은 매칭에 실패해 새로 합성된다(의도된 안전 동작이지만, 대량이면 비용이 붙는다).
- H2 제목은 바꿔도 된다(문장 매칭과 무관) — 예: `## 읽기 전에`가 5번 반복되면 유튜브 챕터가 같은 이름 5개가 되므로, `## 1부 · 읽기 전에`처럼 부 표기를 붙이는 것을 권장. `> 🖼️ 이미지:`/`> 🎬 비디오(I2V):` 줄은 **글자 그대로 유지**(그룹 매칭 키다).
- `> 📥 자산출처:` 줄은 '>' 인용이라 **기존 파서가 조용히 버린다**(sentence-splitter.js:241) → 구버전 앱에서 열어도 대본이 깨지지 않는 하위호환. 신기능만 이 줄을 읽는다.
- 통합대본 파일명은 소스 대본들과 겹치지 않게(스냅샷이 basename 키라 겹치면 .smproj를 서로 덮어쓴다 — main.js:2814).

### 4-2. 왜 대본이 "완전한 .md"여야 하나

- 파서 결정성(F7) 덕에 통합대본을 몇 번을 다시 파싱해도 같은 모델이 나온다 → resplit·재시작·대본수정 경로에서 병합이 사라지는 문제(파서 확장안의 최대 함정)가 원천적으로 없다.
- h2Title이 자연히 실려 ⏱ 타임스탬프(챕터)가 무수정으로 동작한다(App.jsx:189-244).
- 사람이 읽고 검수할 수 있는 기록이 남는다.

### 5-2. 도입부(I2V) 그룹의 특례 — 순서가 중요하다

문/맺음 출력물은 「도입부 비디오 준비」(regroupIntro)를 거친 상태로 스냅샷에 저장돼 있다(문: 이미지 3장 + 비디오 6개). 통합대본을 갓 파싱하면 재배치 전 그룹이라 경계가 다르다. 따라서:

1. 통합대본 파싱 → **문장 자산 먼저 복사**(문장 num·순서는 regroup의 영향을 받지 않는다 — F8)
2. `regroupIntroByTtsDuration`(maxSec 10 — intro-video-prep과 동일 인자)을 실행 — **같은 duration 입력 → 원본과 같은 재배치 결과**
3. 그다음 그룹(이미지·비디오) 매칭·복사

그래도 도입부 일부 그룹이 미매칭이면 그 몇 개만 재생성되게 둔다(비용 소액, 게이트 통과에 필요).

## 6. 함정 목록 (구현자가 밟기 쉬운 순서)

1. 🔴 **원본 폴더를 직접 참조하지 말 것** — sweepBadVisuals가 이상 판정 파일을 실삭제한다(F4). 반드시 복사.
2. 🔴 **ttsDurationSec를 반드시 실어라** — 없으면 4배 과대 추정 + 그룹 길이 누락으로 타임라인이 통째로 왜곡된다(F5). 스냅샷 값 우선, 없으면 ffprobe.
3. 🔴 **14부 스냅샷은 이름·경로가 전부 옛 것**(F10) — basename 재기반 + existsSync 없이 쓰면 전량 미스.
4. **TTS 캐시를 재사용 수단으로 삼지 말 것** — 이번 코퍼스에 대해 이미 무효(F6)이고, 「🗑 TTS 삭제」 한 번에 전체가 날아가는 저장소다. 정본은 "실존하는 파일 경로".
5. **그룹 num은 안정 키가 아니다**(F8 — regroup이 재발번호) → 그룹 매칭은 반드시 imagePrompt 텍스트로. 문장은 텍스트 매칭이므로 안전.
6. **9부는 media-1에 mp4가 0개** — 비디오 매칭 실패를 오류로 취급하지 말고 이미지+켄번스로 자연 진행(기존 동작).
7. **통합대본 basename이 소스와 겹치면 .smproj가 덮인다**(main.js:2814) — 파일명 규칙을 리포트에서 검사.
8. G:(구글드라이브) 스트리밍 — 복사 4천여 회는 retryFs로, existsSync 판정 실패(일시 언마운트)가 게이트 오폭으로 이어질 수 있음을 로그로 남길 것.
9. 통합대본의 `> 🎬 비디오(I2V):` 줄이 videoPrompt로 파싱돼도, 매칭된 videoPath가 있으면 hasVisual(F2)이 생성을 막는다 — 별도 처리 불필요. 단 **비디오 엔진이 grok인 채널이므로 미매칭 그룹이 생기면 브라우저 Grok이 뜰 수 있다** — 매칭 리포트에 "새로 생성될 것" 목록을 명시해 로이가 사전에 알게 할 것.

## 7. 검증 계획 (단계식 — Vrew 로드가 최대 미검증 변수)

0. **매칭 시뮬레이션 재현**(구현 직후 첫 검증 — 이 세션이 이미 돌려 본 것): 통합대본을 파서로 돌리고 소스 7개의 스냅샷·출력폴더와 대조해 문장/그룹 매칭률을 낸다. **기대값 = 문장 4,182/4,182(100%) · 그룹 이미지 80/150 · 비디오 6.** 이 수치가 재현되지 않으면 매칭 로직이 잘못된 것이다. 시뮬레이션 스크립트의 요지: ① 소스 스냅샷을 **옛 이름으로 찾고**(1부=`[서재_0815]`, 2부=`[서재_0817]`, 3부=`[서재_0818]`, 4부=`[서재_0819]`, 5부=`[서재_0820]`) ② `imagePath`/`ttsAudioPath` 는 **basename 만 취해 현재 출력폴더로 재기반** ③ 문장은 `text` 정규화(공백 접기) 일치, 그룹은 `imagePrompt` 정규화 일치.
1. **단위 테스트**(`test/merge-assets.test.js`): 매칭(정상/한 글자 수정→미매칭/섹션 누락/스냅샷 부재 폴백/개명 스냅샷 재기반), 복사 후 게이트 통과, 원본 폴더 무변경 단언, **A/B 역검증**(매칭 게이트를 없애면 대량 재합성 경로로 빠지는 것을 테스트가 잡는지).
2. **미니 통합 실측**: 문 + 1부만으로 통합대본을 만들어 → 이어받기 → 💾 .vrew → **Vrew에서 열기·재생·MP4 내보내기**. (~50분·~700문장 — 기존 실적 범위)
3. **통합1 전체**(4.61h·~4,250문장·~500MB): 빌드 시간·피크 메모리 기록 → Vrew 로드 → 앞/중간/끝 구간 재생 확인 → MP4 내보내기 → 챕터 타임스탬프(⏱) 복사.
4. 성공 시 통합2·3 반복. **실패(Vrew가 못 열면) 폴백**: ① captionMaxChars 상향/disableLongSplit로 클립 수 축소(자막 표시 단위가 달라짐 — 로이 승인 필요) ② 그래도 안 되면 MP4 수준 concat(D안)으로 전환 — 이때도 이어받기 기능은 그대로 유용(반쪽짜리 .vrew 2개로 쪼개 내보내는 변형도 가능).

## 8. 예상 효과

- 재생성 비용 ≈ **0** (미매칭 잔여분만). 이 기능 없이 통합대본을 그냥 「만들기」하면: TTS 재합성 약 12.3시간 분량(RTF 0.455 → **GPU 약 5.6시간**) + 이미지 ~150장 재생성.

- 다음 작품부터는 config §"통합본을 먼저 정하고 회차를 나눈다" 원칙과 결합해, 회차 대본에 잘라낼 부채 자체가 줄어든 상태로 같은 기능을 그대로 쓴다.
