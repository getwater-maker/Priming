# Priming 회원제 · 오류 로그 설계 (2026-10-15)

> 로이 결정(2026-10-15): **결제 회원만 사용** · 회원 관리는 primingwave.com(wise-priming) · 결제는 카드 붙이기 전까지 **통장 입금** ·
> 음성·그림은 **회원이 자기 API 를 연결(BYOK)** · 저장소 `getwater-maker/Priming` **비공개 동의** · 회원당 **PC 2대** · 오류 로그는 **오류가 나면 자동 전송**.
> 이 문서는 서버(wise-priming)와 앱(Priming)이 함께 지키는 **약속(계약)** 이다. 한쪽을 바꾸면 이 문서부터 고친다.

## 0. 왜 이 순서인가

- **사실**: 지금 저장소가 공개라 업데이트 주소(`raw.githubusercontent.com`)로 누구나 프로그램 전체를 받을 수 있다. 로그인 화면만 붙이면 코드에서 지우면 그만이다.
- 그래서 **업데이트를 회원 확인을 거치는 서버에서만** 받게 하는 것이 회원제의 본체다. 로그인 화면은 그 위에 얹는 것.
- ⚠ **비공개 전환은 맨 마지막**. 먼저 바꾸면 새 업데이트 서버를 모르는 모든 PC(로이 메인·아내 PC)가 업데이트를 못 받는다(404 → 전 PC 업데이트 정지).

### 전환 순서 (반드시 이 순서)
1. **서버**(wise-priming): DB·함수·업데이트 중계(§2~§4) — 공개 저장소에서도 동작하게 만들어 둔다.
2. **앱**(Priming): 로그인·회원 확인·새 업데이트 경로(§5) 발행 — 아직 공개 저장소의 옛 경로로 배포된다. 로이 PC 두 대가 이 판을 받고 **관리자로 로그인**.
3. 두 PC 가 새 경로로 업데이트되는 것을 확인(`update:verify` 를 새 경로로).
4. 그 뒤에 저장소 **비공개** 전환(로이가 GitHub 설정에서 · 또는 로이 승인 뒤 `gh repo edit --visibility private`).
5. 회원용 설치본(`npm run dist`)은 비공개 Release 로 두고 §4 중계로만 내려준다.

## 1. 회원 = 무엇으로 판단하나

- primingwave.com 기존 테이블을 그대로 쓴다: `programs`(slug **`priming-app`** 추가) · `cohort_programs` · `enrollments(status, expires_at)` · `admins`.
- **유효 회원** = `admins` 에 있거나, `enrollments.status='active'` 이고 `expires_at is null or expires_at > now()` 인 기수가 `priming-app` 프로그램에 접근 권한이 있는 사람.
- 통장 입금 단계: 입금 확인 → 관리자 화면에서 등록 + 만료일 입력(지금 관리자 화면으로 가능). 카드 결제는 나중에 같은 `enrollments` 행을 자동으로 만든다(앱은 바뀌지 않는다).
- 가입 때 약관·개인정보 동의는 기존 `user_consents` 를 쓴다. **오류 로그 자동 전송**을 개인정보 처리방침에 적는다(무엇을·얼마나 보관하는지 §6).

## 2. 서버 — DB (wise-priming 마이그레이션)

```
app_devices(user_id uuid → auth.users, device_id text, name text, first_seen timestamptz, last_seen timestamptz,
            primary key(user_id, device_id))
app_error_logs(id bigserial, user_id uuid, device_id text, app_version text, created_at timestamptz default now(),
               kind text check (kind in ('auto','report')), summary text, body text)   -- body ≤ 64KB(앱이 자른다)
```
- 기기 상한 = **2**(설정값 · 회원별 예외가 필요하면 `enrollments` 에 칸을 더한다). 관리자는 상한 없음.
- RLS: 본인 행만 SELECT/DELETE(기기 해제는 사이트 「내 기기」에서) · 로그는 본인 INSERT 만, 읽기는 관리자만.
- 로그 보관 30일(매일 지우는 예약 SQL 또는 Edge Function cron).

### RPC (security definer · 앱은 Supabase REST 로 부른다)
- `priming_license(p_device_id text, p_device_name text)` → `{ ok, member, admin, expires_at, devices:[{device_id,name,last_seen}], reason }`
  - 회원이 아니면 `ok=false, reason='not_member'` · 만료면 `'expired'`.
  - 처음 보는 기기이고 이미 2대면 `ok=false, reason='device_limit'`(목록을 돌려줘 앱이 「사이트에서 기기 해제」를 안내).
  - 통과하면 `app_devices.last_seen` 갱신.
- `priming_log(p_device_id, p_app_version, p_kind, p_summary, p_body)` → 하루 기기당 **30건** 넘으면 버린다(폭주 방지 · 무료 등급 보호).

## 3. 앱 로그인 방식

- **Supabase 이메일·비밀번호 로그인**을 앱 main 에서 REST(fetch)로 — ⛔ npm SDK 추가 금지(라이트 업데이트가 막힌다). 소셜 로그인 회원은 사이트에서 비밀번호를 정하게 하거나, 2단계에서 「브라우저로 로그인」(로컬 주소로 돌아오기)을 더한다.
- 받은 access/refresh 토큰은 `safeStorage` 로 암호화 저장(⛔ 렌더러로 돌려주지 않는다 · 평문 금지 — 기존 자격증명 규칙).
- `device_id` = 처음 실행 때 만든 무작위 UUID(`~/.priming-maker/device.json`) · 이름 = 컴퓨터 이름.
- 앱을 켤 때 `priming_license` 확인. **인터넷이 안 되면 마지막 성공 뒤 7일까지** 그대로 쓴다(그 뒤엔 로그인 화면).
- 회원이 아니면: 로그인 화면 + 「primingwave.com 에서 가입·입금 안내」 링크. 제작 기능은 열지 않는다.

## 4. 업데이트 중계 (저장소 비공개 뒤에도 회원만 받게)

- **Cloudflare Worker**(무료 하루 10만 요청) `updates.primingwave.com`:
  - `GET /manifest` · `GET /file/<경로>` — 헤더 `Authorization: Bearer <Supabase access token>` 를 Supabase 로 확인 + `priming_license` 와 같은 회원 판정 → 통과하면 **비공개 저장소의 raw 파일**을 서버 쪽 GitHub 읽기 전용 토큰으로 받아 그대로 준다.
  - ⛔ GitHub 토큰은 Worker 비밀값에만(앱·저장소·로그에 없음).
  - 설치본(.exe)도 같은 방식(비공개 Release 자산).
- 앱 `light-updater.js`: 주소를 Worker 로 바꾸고 토큰 헤더를 단다. **「전부 받아 해시 확인 → 그 뒤에만 교체」 규칙은 그대로**(`test:updater`). 토큰이 없거나 만료면 업데이트를 건너뛰고 지금 판으로 켠다(⛔ 업데이트 실패로 앱을 막지 않는다 — 회원 확인은 §3 이 한다).
- `update:verify` 도 Worker 경로로 확인하게 고친다(관리자 토큰).

## 5. 앱이 함께 바꿔야 하는 것 (BYOK)

- **로이 전용 기본값을 걷어낸다**: OmniVoice·ComfyUI 기본 주소 `DESKTOP-CBQLOLJ`·Tailscale 이름, 참조음성 서버 동기화, 썸네일 기본 폴더(`D:\## 아도나이로이\…` — 있을 때만 쓰므로 무해하지만 회원 화면엔 안 보이게), 유튜브 업로드 공용 연결 등. → 관리자(로이)일 때만 지금 기본값, 회원은 빈 값 + ⚙ 설정에서 자기 주소·키.
- API 키는 지금처럼 PC 안 `safeStorage`(서버로 보내지 않는다 — 사이트의 BYOK 와 다른 점: 앱은 로컬에서 쓴다).

## 6. 오류 로그 자동 전송

- **언제**: 로그에 오류 줄(`✗`·`❌`·`🐞 화면 오류`·잡히지 않은 예외)이 찍히면 → 60초 모아서 한 번 보낸다(같은 오류 반복은 한 번).
- **무엇을**: 그 오류 앞 **200줄**(그날 로그 파일에서) + 앱 버전 + 기기 id. 64KB 에서 자른다.
- **지우고 보낸다(필수)**: API 키 모양(`sk-…`·`AIza…`·`hf_…`·긴 16진/base64 토막) · 이메일 · 사용자 폴더 경로(`C:\Users\<이름>` → `~`) · 전화번호. 지우는 규칙은 한 곳(`core/log-scrub.js`) + 시험(판정력 포함).
- **수동 보고**: 로그 상자 「🐞 문제 보고」 = 그날 로그 전체 + 회원이 쓴 설명(`kind='report'`).
- 회원이 ⚙ 에서 자동 전송을 끌 수 있다(기본 켬 · 처리방침에 명시).
- **로이가 보는 곳**: primingwave.com 관리자 「Priming 오류」 화면 — 회원·기기·버전·날짜로 거르고 본문을 본다.

## 7. 비용 (무료 등급 안)

- Supabase 무료: DB 500MB — 로그 64KB × 하루 기기당 30건 상한 × 30일 보관이면 회원 수십 명까지 여유. 넘으면 보관일을 줄인다.
- Cloudflare Worker 무료 하루 10만 요청 — 업데이트는 바뀐 파일만 받으므로 충분.

## 7-1. 서버 세션이 더한 것 (2026-10-15 · wise-priming `cbcc26e` · 로이 확인)

- RPC `priming_status()` — 기기 등록 없이 회원 여부만(Worker·사이트 「내 기기」가 쓴다).
- 로그 상한에 **회원당 하루 60건**(기기 id 를 바꿔 가며 쏟아 내지 못하게) — 기기당 30건과 함께.
- 구글로 가입한 회원은 사이트 「🖥 내 기기」(`/member/devices`)에서 **앱 비밀번호**를 정한다(앱은 이메일·비밀번호 로그인).
- 회원 등록 = 전용 기수 「Priming 앱 회원」(slug `priming-app`) + 만료일. ⚠ 프로그램을 「모든 기수」에 붙이는 마이그레이션은 이 기수를 뺀다.
- Worker 주소: `/health` · `/manifest` · `/file/<조각별 인코딩 경로>` · `/installer` · `/installer/info` · 응답 401 `no_token`/`invalid_token` · 403 `not_member`/`expired` · 400 `bad_path` · 404 `not_in_manifest` · 502 `upstream`/`auth_unavailable`.
- 운영 값: Supabase `https://tvvcwhxullrwpsitmyep.supabase.co` · 공개 키(publishable)는 앱 `core/license` 에 · Worker 변수 `SUPABASE_URL`·`SUPABASE_ANON_KEY`(= publishable)·`GH_*` · `GITHUB_TOKEN` 은 비공개 전환 직전에(Secret 종류로).

## 7-3. 포인트 표시 약속 (v0.9.72)

- `priming_license` 응답에 `points_granted`·`points_remaining`(숫자)이 있으면 앱 헤더에 「🪙 남은 N / 지급 M」. 요청서 `docs/요청서_wise-priming-포인트.md`.
- **서버가 한 것(2026-10-18, wise-priming 마이그레이션 `034_priming_points.sql` — 로이가 SQL Editor 에서 실행해야 켜진다)**: 원장 `app_point_ledger`(지급·조정·차감·환불, 잔액 = 합계) · `priming_license` 성공 응답에 `points_granted`(지급+조정 합계)·`points_remaining`(전체 합계) 추가 — **원장이 비어 있는 회원·관리자는 두 칸 생략** · 관리자 화면 「Priming 앱 → 회원·기기」 에 지급 입력 · 차감 초안 `priming_points_spend(p_device_id, p_amount, p_kind, p_ref)` → `{ok:true, charged, points_remaining…}` / `{ok:false, reason:'no_points'|'duplicate'|'invalid_amount'|'unknown_device'|not_member…}`(ref 는 시도마다 고유, 1회 최대 10,000pt, 관리자 계정은 charged=0) · 환불 초안 `priming_points_refund(p_device_id, p_ref)`(같은 ref 의 차감을 한 번만 되돌림). 차감 기준은 미확정이라 앱은 아직 spend 를 부르지 않는다.

- **차감 대상·가격 정책 확정(로이 2026-10-18 — 1번)**: 제1 목표는 **프로그램 사용권 판매**, 포인트는 편의 서비스다 — 앱 기능은 포인트 없이도 전부 쓸 수 있어야 한다(⛔ 포인트로 기능을 잠그지 않는다).
  - 사용 방식 3갈래(회원이 고른다): 🖥 내 PC(로컬) 0pt · 🔑 내 API 키(BYOK — kie 개인 키 포함) 0pt · ☁ **우리가 제공하는 API(kie 이미지·영상, 가능하면 TTS)만 차감**.
  - 🗑 **ComfyUI 클라우드는 회원에게 제공하지 않는다**(로이 구독은 2026-10 말 해지 · 이후 kie 로만) — 회원용 차감 표에 넣지 않는다.
  - 차감량 = kie 크레딧 1:1(`core/kie-models` 표 한 곳). **마진은 차감량이 아니라 포인트 판매 단가에서 원가의 약 1.3배**(순마진 약 10~15% — 결제 수수료·부가세·환율 감안 · 판매가 확정 전 세무 확인) — 앱·서버 차감 로직에 마진을 넣지 않는다.
  - **표시 시점 확정(2번 · 2026-10-18 · 로이가 클로드에게 위임)**: ① 헤더 「🪙 남은/지급」 유지(값 없는 회원은 숨김 · 10% 이하 붉게) ② 엔진 목록 항목 옆에 「약 N pt/장」(로컬·내 키는 「내 PC」·「내 키」) — 서비스 이름·달러 금지 ③ **예상 합계 100pt 이상인 작업(영상·큐 ⚡)만 시작 전 「약 N pt · 남은 M pt」 확인**(큐는 `_batchPreflight` 에 합산 · 그 밑은 조용히 진행) ④ 차감·환불 직후 헤더를 바로 갱신(5분 폴링 안 기다림) · 환불은 로그 한 줄 ⑤ 포인트를 누르면 최근 차감 내역 팝업(서버 원장 조회 RPC 하나 추가).
  - **최종 정책 7개(로이 확정 2026-10-18)**: ① 차감은 우리가 제공하는 API(kie 이미지·영상, 가능하면 TTS)만 · **정수 pt 올림**(예: Z-Image 0.8→1pt) · 내 PC·내 API 키 0pt. ② **사용권 구매 시 기본 100pt 무상 지급 = 이미지 최저가 모델(Z-Image) 기준 100장**(로이 원가 약 $0.40) — 홍보 문구는 「기본 이미지 모델 기준」 조건을 함께 적는다(Nano Banana 2.1 은 4pt → 25장이라 조건 없는 「100장」은 과장). ③ 추가 포인트 = 선불 팩, 판매 단가 원가 약 1.3배 · 상품 A 프로그램 단독(기본 100pt 포함) / B 프로그램 + 포인트 팩. ④ 유효기간 없음·누적(kie 이용약관 4조 「never expire」와 같은 기준). ⑤ **환불 = 구매 후 7일 이내 미사용분은 환불, 사용분은 환불 불가** — 구매 화면·약관에 눈에 띄게 표시(전자상거래법상 철회 제한 표시·입증 책임은 사업자 몫 · 대법원 2018다214746) · **무상 포인트는 환불 대상 제외**(장부에서 유상/무상 구분). ⑥ 시작 전 모자라면 막고 「내 PC·내 키로 바꿔서 계속」 안내. ⑦ **약관·선불전자지급수단(전자금융거래법) 해당 여부는 전문가 확인 후 확정.** ✅ **kie 재판매 확인 완료(2026-10-18 · kie 디스코드 지원팀 답변)**: ⓐ 회원이 자기 kie 계정·키를 앱에 넣는 것 = 허용 ⓑ **우리 백엔드·우리 API 키로 회원 대신 호출하고 우리 포인트 시스템으로 과금하는 것 = 「entirely welcome」** ⓒ 단 리셀러·파트너·엔터프라이즈·제휴(추천 수수료) 프로그램은 **없다 → 도매 할인·제휴 수익 없음**(마진은 포인트 판매 단가 1.3배에서만). ⚠ 지원팀 채팅 답변이라 정식 계약서가 아니다 — **채널 대화 캡처를 보관**(분쟁 근거) — 보관 위치 `D:\Priming_증빙\kie-재판매허용-디스코드답변-2026-10-18.png`(저장소 밖 · ⛔ 저장소에 넣지 않는다: 계정 이름이 보이고 업데이트로 전 PC 에 퍼진다).
  - **무상 포인트 회수(로이 확정 2026-10-18)**: 기본 지급 100pt 는 **프로그램 사용기한(1개월)까지만 쓸 수 있고, 사용기한이 끝나면 남은 무상분은 회수**한다. **유상(구매한) 포인트는 회수하지 않고 누적**(사용권을 갱신하면 다시 쓴다). 차감 순서 = **무상(만료 임박) 먼저 → 유상**. 기본값(바꾸기 쉬움): 사용권을 갱신하면 새 100pt 를 지급하되 이전 무상분은 이월하지 않는다. 구매 화면·약관·홍보 문구에 「기본 포인트는 사용기한 내 사용」 을 적는다.
  - **임의·이벤트 지급(로이 2026-10-18)**: 관리자가 회원에게 임의로 지급·회수(사유·만료일 지정) · 이벤트는 일괄 지급(미리보기·확인) 또는 이벤트 코드(1인 1회·기한·수량) — 서버 요청서 `docs/요청서_wise-priming-포인트.md` 「추가 요청」 · 이벤트·임의 지급분은 기본 무상(환불 제외).
  - **포인트 구매(결제) = 사이트 결제 페이지 + 일회용 코드로 앱에서 열기**(앱은 카드 정보를 다루지 않는다 · URL 에 토큰 금지) · 서버 요청서 `docs/요청서_wise-priming-포인트결제.md` · kie 는 로이 카드 자동 충전(캡처로 확인 2026-10-18 — 기준·충전량·10분에 1회 제한) · kie 제휴 프로그램 15%(승인 신청 대기 — 승인되면 앱 키 발급 안내에 추천 링크 + 대가 표시).
  - 🔴 **구조 과제**: 회원이 우리 API 를 쓰려면 **kie 키를 회원 앱에 둘 수 없다**(지금 앱은 키를 로컬 secret-store 에 둔다 = 관리자 전용). 서버(wise-priming Worker 등)가 회원 토큰을 확인하고 포인트 차감 → kie 호출 → 결과 URL 전달을 **대행**해야 한다. 앱은 결과를 즉시 내려받는다(kie 생성물 14일 뒤 삭제). 로이 kie 잔액(선결제) ≥ 회원 미사용 포인트 합계(부채)를 서버가 감시한다.
  - 포인트가 모자라면 **시작 전에 막되**, 「내 PC·내 키로 바꿔서 계속」을 안내한다. 실패·중단은 환불.
