### A-2. 🙋 시작 전에 정할 것 (판단 — 확신도 중간)

1. ✅ **어떤 책을 올리나 — 만드는 전자책은 모두 올린다**(로이 2026-11-11: 「팔리면 좋고 안 팔리면 할 수 없다 — 대신 팔리도록 최대한 만들고 결과를 받아들인다」). 그래서 도구는 **한 권 → 크몽 등록 한 벌**이 반복되도록 만든다. 덧붙이는 것 두 가지:
   - 처음 **2~3권은 먼저 올려 심사 결과를 본 뒤** 나머지를 올린다. 반려 사유(분류·문구·이미지)는 모든 책에 똑같이 걸리므로, 먼저 고쳐 두면 반려를 한꺼번에 맞지 않는다.
   - 고전 소설이 들어갈 1차 분류가 있는지는 첫 화면 실측 때 확인한다(승인 뒤에는 1차 분류를 바꿀 수 없다 ✅ posts/755). 책마다 조회·판매를 기록해 「무엇이 팔리나」를 데이터로 남긴다.
   - **실측 결과(2026-11-11): 소설·문학·고전 칸이 없다.** Claude 잠정 결정(로이 「그렇게 진행해」): 고전·번역서는 **해설이 붙은 책만 「학습·교육 전자책 > 기타」**, 해설 없는 순수 소설·번역본은 크몽에 올리지 않는다(맞지 않는 칸 = 판매 약관 제9조 카테고리 부정등록). 첫 시험 2~3권 중 **고전은 한 권만** · 반려되면 크몽에서 고전을 접는다 · AI 활용은 상세페이지에 밝힌다. 확신도 낮음~중간 — 첫 심사 결과로 확정.
2. **「수정 제한」(PDF 암호·권한).** 지금 쓰는 PDF 라이브러리(pdf-lib)는 암호를 걸지 못한다. 그래서 EPUBCheck 처럼 **저장소 밖 `~/.priming-maker/tools/qpdf`** 에 두고 「있으면 건다 · 없으면 점검표에 ✋」로 하자는 안이다. npm 의존성은 늘리지 않는다.
3. **워터마크 문구**(예: `ⓒ 출판사명 · 무단 복제·배포 금지`) · 저작권 안내 쪽 문안. 법 조항 문안은 로이가 확정한다.
4. **수익·경력 문구.** 크몽은 증빙을 요구한다. 상세페이지에 이런 문구를 쓰려면 증빙 자료가 필요하다.

### A-3. 만드는 것

#### ① 크몽판 PDF = 판(edition) 하나 더
- 지금 판은 `print`(종이책)·`ebook`(전자책)이다. 여기에 **`kmong`** 을 더한다(`buildBookHtml({edition:'kmong'})`). 원고(BookModel)는 그대로 두고 조판만 다르게 한다.
- 규격 값은 **`platform-presets.PLATFORMS.kmong` 한 곳**에 둔다: `trims:['A4']`, `fontPt:12`, `lineHeight:1.5`, `minBodyPages:20`, `maxImageRatio:0.3`, `maxBytes:200MB`, 메인 이미지 652×488 등. 값마다 출처 URL과 확인일을 주석으로 단다(`price-calc.RATES` 와 같은 원칙).
- 크몽판만의 조판:
  - 첫 쪽: 표지(전자책 앞표지와 같은 출처 — `resolveEbookCover`)
  - **저작권 안내 쪽**: 표지 다음 쪽과 맨 끝 쪽. 문안은 원고 메타 `> 크몽안내:` 또는 기본 문안
  - 목차: 쪽 번호가 있어야 한다. 지금 내지 목차 기능을 그대로 쓴다
  - **워터마크**: `@page` 배경 글자로 모든 쪽에 옅게. 본문 글자를 가리지 않도록 불투명도와 위치를 정한다
  - 판권: 전자책 판권과 같다. 종이책 정가는 넣지 않는다
- 「A4 기본 여백」⚠️: 한글·워드의 기본 여백이 서로 다르다. 우선 위·아래 20mm · 좌·우 25mm 를 쓰고 첫 등록 때 확인한다.
- 출력 폴더: `out-layout` 에 `완성/크몽/{01_완성본, 02_메인이미지, 03_상세페이지, 04_미리보기}` 를 더하고 이름 접두는 `[크몽] `. 🔴 `bookOutputKind` 는 접두로 가른다 — `[크몽]` 파일을 전자책으로 잡지 않게 한다(v0.9.13 사고와 같은 계열).

#### ③ 메인 이미지·미리보기 그림
- 메인 이미지 652×488: 앞표지 + 제목 + 한 줄 소개를 **B 의 같은 HTML 렌더러**로 굽는다. 유색 배경을 쓰고, 중요한 요소는 사방 50px 안쪽에 둔다(점검 포함).
- 미리보기 5~9장: **완성 크몽판 PDF 의 쪽을 mupdf 로 PNG 로 바꾼다**. 화면에서 고를 수 있게 하고, 기본은 목차 1쪽 + 본문 앞부분 4쪽이다. 흐림·가림은 하지 않는다(크몽 금지).

#### ④ 크몽 등록 = **자동 입력(입력·첨부까지)** + 복사 도우미
- ✅ 로이 2026-11-11 「크몽에도 자동 입력이 필요하다」 → **부크크 방식**(`register-fill`·`register-browser`)을 따른다: 앱의 자동화 브라우저(playwright 프로필 · 로그인은 로이가 한 번)에서 칸 입력·파일 첨부·다음 단계 이동까지. 🔴 **최종 「제출/심사 요청」 클릭은 하지 않는다**(로이가 직접 · 시험이 소스를 검사) · 칸을 읽어 되짚고 단계마다 `_등록캡처/` 에 캡처 · 앞 단계가 실패하면 넘어가지 않는다.
- 🔴 **칸 이름·순서는 로그인 상태로 실측한 뒤에만 코드에 넣는다**(부크크 원칙). 실측은 별도 세션에서 ego-lite 로 읽기만 한다(저장·제출 금지) · 그때 크몽 이용약관·운영정책의 자동화(매크로) 조항도 함께 확인한다 — 금지 조항이 있으면 자동 입력을 접고 복사 도우미만 둔다.
- 복사 도우미는 그대로 둔다(자동 입력이 막힐 때의 대안).
- 입력값은 `기준\등록\<원고이름>.크몽등록정보.md` 에 둔다(`## [섹션]` + `- 키: 값`, 원고 메타보다 우선). 양식 정본은 `docs/양식/크몽등록정보_양식.md`.
- 섹션: 서비스 제목 · 카테고리 · 패키지(최대 3단 — **1만 원 차이**를 점검) · 서비스 설명 · 목차(원고에서 자동) · 저자 소개 · FAQ · 환불 안내.

### A-4. 🔴 금지선
- 크몽 최종 제출(심사 요청) 클릭 금지 · 실측 전 칸 이름을 추측해 넣지 않는다(위 ④).

## B. 상세페이지 만들기

### B-1. 목표
책 한 권의 판매용 상세페이지를 **세로로 긴 이미지(PNG 조각)** 로 만든다. 첫 용도는 크몽이고, 같은 결과물을 부크크 소개·블로그·스마트스토어에도 쓸 수 있다. 판매처마다 폭만 다르다(크몽은 가로 652~2,000px · 조각 세로 3,000px 이하 · 최대 9장 ✅ 실측 — 기본 860px 은 이 범위 안 · 1,000px 등은 프리셋으로).

### B-2. 흐름

```
책 정보(원고 메타·목차·저자소개·표지)  ─┐
상세 원고  기준\상세\<원고>.상세.md       ─┼─▶ core/book/detail-page.js ─▶ HTML 한 벌
(Claude 초안 → 로이가 고침)              ─┘        (순수: 데이터 → HTML)      │
                                                                      ├─▶ 오른쪽 미리보기(iframe)
                                                                      └─▶ core/book/detail-render.js
                                                                           playwright 크로미움 fullPage 캡처
                                                                           → 세로 3,000px 이하로 자름 → PNG
```

- **같은 HTML** 을 미리보기와 PNG 가 함께 쓴다. 🔴 미리보기용 배치를 따로 계산하지 않는다(정보 카드·화면 카드에서 지켜 온 원칙 그대로).
- 렌더: `register-browser`·`pdf-builder` 가 이미 쓰는 **playwright 크로미움**(`chromiumPath()`)으로 `page.screenshot({fullPage:true})` 한다. 새 의존성은 없다. Electron 숨김창의 capturePage 는 화면 크기 제한 때문에 쓰지 않는다.
- 자르기: 문단(섹션) 경계를 우선해 3,000px 이하로 자른다 → `[크몽] <권>_상세_01.png …`. 하나로 이어 붙인 판(`_상세_전체.png`)도 함께 낸다.
- 글꼴: **동봉 글꼴만** 쓴다(Noto Serif KR·HanjaSerif·Pretendard-Bold). 🔴 새 글꼴 동봉은 로이 승인 뒤에.

### B-3. 상세 원고 형식 (`<원고>.상세.md`)

정해진 섹션을 순서대로 둔다. 비어 있는 섹션은 건너뛴다. 「자동」 섹션은 원고에서 가져온다.

## C. main.js 기능별 분리

### C-1. 지금 상태 (실측)
- `main.js` **14,412줄 · 1.1MB · IPC 약 351개**. 최근 30일 커밋 315개 중 **139개가 main.js 를 고쳤다**.
- 분리된 묶음은 `core/book/resubmit-ipc.js` 하나뿐이다. 이 파일의 `install({ipcMain, dialog, shell, win, context, …})` 꼴이 그대로 본보기가 된다.
- 권위 상태 `S` 의 `parsed·scriptPath·outRoot·preset·mode` 는 `world-ctx` 의 getter 다. IPC 는 `WORLD.wrapHandle(ipcMain)` 을 거쳐 세계(롱폼/출판)가 정해진다.

### C-2. 방식
- **새 폴더 `ipc/`**(최상위)에 기능마다 파일 하나를 둔다. 각 파일은 `install(ctx)` 를 내보낸다.
  - `core/` 에 두지 않는 까닭: `core/*.js` 는 렌더러 번들에도 들어간다. IPC 모듈은 electron 을 require 하므로 섞이면 안 된다.
  - 이름이 `scripts` 인 폴더는 매니페스트에서 빠지므로 쓰지 않는다. `ipc/` 는 그대로 배포된다(C-4 시험으로 확인).
- `ctx` 하나로 넘긴다: `{ ipcMain: 감싼 ipcMain, S, WORLD, ED, win, log, P, … 그 기능이 쓰는 main 내부 함수 }`.
  - 🔴 **반드시 감싼 `ipcMain`** 을 넘긴다. 날것을 넘기면 세계 배정(`book-` → 출판)이 빠져 롱폼 대본이 섞인다.
  - main 내부 함수를 넘길 때는 「지금 그 기능만 쓰는 함수」는 함께 옮기고, 여러 기능이 쓰는 함수(`pushDtoUpdate`·`bookSpec` 등)는 ctx 로 넘긴다.
- 판 전용 기능은 `if (ED.has('x')) require('./ipc/x').install(ctx)` 로 한 줄에 묶는다. `FEATURES.files` 에 `ipc/x.js` 를 넣으면 판매판 매니페스트에서 자동으로 빠진다 — 판 나누기도 함께 깔끔해진다.
- **한꺼번에 옮기지 않는다.** 그 기능을 고칠 일이 생겼을 때 그 묶음만 옮기고, 옮기는 커밋에는 **동작 변경을 섞지 않는다**(옮김만 하는 커밋 따로 · 고침 커밋 따로).

### C-3. 순서

| 단계 | 대상 | IPC | 까닭 |

### C-4. 안전망
- **정의 안 된 이름 검사**: eslint 를 **devDependencies** 에만 넣고 규칙은 `no-undef` 하나만 켠다(`npm run lint:undef` — main.js·ipc/·core/). 근거: `scripts/gen-manifest.js:136` 이 deps 해시를 **`dependencies` 만으로** 계산한다 → devDependencies 는 라이트 업데이트를 막지 않는다(실측). 🙋 dev 도구 하나가 늘어나는 것에 대한 로이 승인.
- 옮길 때마다: `lint:undef` → `test:makeall` → 그 기능의 시험(출판이면 `test:book`) → `test:world`(세계 배정) → `test:edition`(판매판에서 빠지는지).
- 새 시험 `test:ipcsplit`: ① 옮기기 전과 후의 **IPC 채널 이름 목록이 같다**(빠지거나 겹친 채널 0) ② `ipc/*.js` 가 날것 `require('electron').ipcMain` 을 쓰지 않는다 ③ 매니페스트에 `ipc/` 가 들어 있다.
- 규칙 한 줄을 CLAUDE.md §3 에 더한다: 「**새 IPC 는 main.js 에 넣지 않는다 — `ipc/<기능>.js`**」.

### C-5. 효과 측정
- main.js 줄 수, 그리고 **최근 30일 커밋 가운데 main.js 를 고친 비율**(지금 44%)을 C 단계마다 작업노트에 적는다. 이 비율이 내려가야 세션끼리 부딪힘과 AI 읽기 비용이 실제로 줄어든다.
