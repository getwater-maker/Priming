# 요청서 — Priming 이용 신청: 기간 고르기 + 결제(입금 → 관리자 「입금 확인」 한 번 / 카드 → 승인 즉시) (2026-11-05)

> ⛔ **2026-11-05 오후 로이 결정으로 [`요청서_wise-priming-기간선택가입.md`](요청서_wise-priming-기간선택가입.md)가 이 요청서를 대신한다**(기간 고르기·입금 안내를 앱 안에서 · 1·3·6·12개월 · 가입 코드는 앱에 접어 둔 채 남김). 아래는 기록용 — 서버 뼈대(기간 여는 함수 하나 · 값 복사 · 카드 자리)는 새 요청서로 옮겼다.

> 보내는 곳: wise-priming 세션 · 보낸 곳: Priming 세션 · 로이 결정 2026-11-05
> 바뀌는 앞 요청: [`요청서_wise-priming-앱가입.md`](요청서_wise-priming-앱가입.md)(가입 코드 · DB 035) — 코드 기능은 **지우지 않고 관리자 전용으로 남긴다**(이벤트·지인 제공용). 회원이 이용을 시작하는 기본 길만 이 요청서의 「신청 → 결제」로 바꾼다.

## 왜

- 지금 앱 이용을 시작하려면 **로이가 코드 만들기 → 메일로 보내기 → 회원이 받아 넣기** 세 단계가 있다. 로이: 「너무 복잡해」.
- 사이트에도 신청서(주문)를 저장하는 곳이 없다 — 강의·앱 모두 「메일로 신청 → 계좌 안내 → 입금 → 관리자가 손으로 등록」(`src/lib/course.ts` · `member/devices` 문구).
- 원하는 것: **회원은 가입할 때 기간을 고르고 결제 방법을 고른다. 입금이면 관리자 화면에서 「입금 확인」 한 번 누르면 바로 쓸 수 있고, 카드면 승인되자마자 쓸 수 있다.**

## 회원 흐름

1. 가입(Google 한 번 또는 이메일 — 지금 그대로).
2. **이용 신청 화면**(예: `/priming/order` — 주소는 서버 세션이 정해 알려 달라)
   - 이용 기간 고르기(요금표 — 아래 「요금표」)
   - 결제 방법 고르기: **통장 입금** / **카드**(지금은 「준비 중」으로 비활성 표시)
3. **통장 입금**을 고르면 그 화면에서 바로 계좌 · 금액 · **입금자명**이 보인다 → 신청서가 `pending`(입금 대기)으로 저장된다. 같은 내용을 회원 이메일로도 보내면 좋다(선택).
   - 이미 입금 대기 신청서가 있으면 새로 만들지 않고 그것을 보여 준다(중복 신청 방지 · 기간을 바꾸면 그 신청서를 고쳐 쓴다).
4. 회원 화면(`/member/devices` 등)에 「입금 확인 대기 중 — 기간 N개월 · 금액」 상태가 보인다.
5. 관리자가 확인하면 바로 이용 가능 → 앱 로그인 화면에서 「다시 확인」만 누르면 들어간다.

## 관리자 흐름

- 관리자 화면 「Priming 앱」에 **「이용 신청」 탭**(가입 코드 탭 옆).
  - 목록: 신청 시각(KST) · 이메일 · 기간 · 금액 · 입금자명 · 상태(입금 대기 / 완료 / 취소 / 기한 지남).
  - 각 줄에 **「입금 확인」** 버튼 → 확인창 한 번 → **그 즉시 기간이 열리고 크레딧이 들어간다.** 회원에게 「이용이 시작됐습니다」 메일(선택).
  - **「취소」** 버튼(잘못 신청 · 환불).
- 입금 대기 신청서는 **7일 지나면 「기한 지남」**으로 보이게(자동 삭제는 하지 않는다 — 늦은 입금이 들어오면 관리자가 그대로 「입금 확인」을 누를 수 있게).

## 서버 — 한 곳 원칙 (🔴 중요)

- **기간을 여는 함수는 하나**: 예) 내부 함수 `_priming_grant(p_uid, p_days, p_points, p_tier, p_note)`.
  - 지금 `priming_redeem_code` 안에 있는 「enrollments 만들기 / 이미 유효하면 만료일 + days 로 연장 / 제한 없음 회원은 그대로 / `_priming_points_credit`」 부분을 이 함수로 **옮기고**, 코드 사용 · 입금 확인 · (나중) 카드 승인 세 곳이 모두 이것만 부른다. ⛔ 기간 계산을 세 곳에 따로 쓰지 말 것(Priming 저장소의 단골 사고가 「같은 일을 하는 코드가 여러 곳」이다).
- 테이블(예시 — 이름은 서버 세션이 정한다):
  - `app_plans(id, label, days, price_krw, points, tier, on_sale, sort_order)` — **요금표는 관리자 화면에서 고칠 수 있게**(가격이 아직 미정이다 · 아래).
  - `app_orders(id, user_id, plan_id, days, price_krw, points, tier, method('bank'|'card'), status('pending'|'paid'|'canceled'), depositor, created_at, paid_at, paid_by, pg_tid, note)` — **신청 순간의 기간·금액·크레딧을 복사해 둔다**(나중에 요금표를 바꿔도 이미 낸 신청서는 그대로).
- RPC:
  - `priming_order_create(p_plan_id, p_method)` — 로그인 회원 · 입금 대기 중복 방지 · 돌려줌 `{ok, order:{id, days, price_krw, depositor, bank:{은행, 계좌, 예금주}}}`.
  - `priming_order_mine()` — 회원 화면·앱 안내용(가장 최근 신청서 상태).
  - `admin_priming_order_confirm(p_order_id)` — 관리자만 · `pending` 일 때만 · **두 번 눌러도 기간이 두 번 붙지 않게**(행 잠금 + 상태 확인) → `_priming_grant`.
  - `admin_priming_order_cancel(p_order_id, p_note)`.
  - `admin_priming_orders_list(...)`, `admin_priming_plans_*`(요금표 고치기).
- 계좌 정보는 코드에 박지 말고 설정(관리자 화면 또는 환경값)에서 읽는다.
- **카드(나중)**: 결제 대행사 승인 알림(웹훅)을 받는 서버 경로 하나 → 서명 검증 → 금액이 신청서와 같은지 확인 → `app_orders` 를 `paid` 로 → `_priming_grant`. 이번 요청에서는 **자리만 만들어 두고(결제 방법 `card` 는 「준비 중」)** 대행사는 로이가 정한 뒤 따로 요청한다.

## 요금표 — 로이가 아직 정하지 않은 값

- 기간 종류·가격·기간마다 크레딧 — **미정**. 관리자 화면에서 고칠 수 있게 만들고, 처음 값은 `on_sale=false` 로 넣어 두면 로이가 정해서 켠다.
- 입금자명 규칙 — 제안: 강의와 같이 **가입 이메일 앞부분**(사람이 다르게 넣어도 관리자가 목록에서 금액·시각으로 찾을 수 있으니 강제하지 않는다).
- 입금 대기 기한 — 제안 **7일**(위 「기한 지남」).

## Priming 앱 쪽(이 세션이 한다 — 서버가 끝나면)

- 로그인 화면의 「가입 코드」 칸과 「가입 코드로 이용 시작」 단추를 뺀다 → **「이용 신청하기」**(사이트 신청 화면을 연다 · 주소는 `primingwave.com` 고정 주소 하나) + 「다시 확인」.
- 입금 대기 신청서가 있으면 로그인 화면 안내 문구를 「입금 확인 대기 중입니다(기간 · 금액). 확인되면 바로 쓸 수 있습니다」로(`priming_order_mine` 을 부를 수 있으면 · 없으면 고정 문구).
- 가입 코드 입력은 앱에서 없어진다. 코드를 받은 사람은 **사이트 회원 화면에서** 넣게 해 달라(지금 사이트에 코드 입력 칸이 없다면 하나 — 관리자가 만든 코드는 계속 쓸 수 있어야 한다).

## 회신해 달라

- 신청 화면 주소 · 회원 화면에서 신청 상태가 보이는 곳 · 마이그레이션 파일 이름(로이가 SQL Editor 에서 실행) · RPC 이름·응답 꼴 최종본 · `priming_order_mine` 을 앱이 부를 수 있는지(토큰 · 공개 키).
- 사이트 코드 입력 칸 위치.
- 배포 순서: **사이트 신청 화면이 먼저**, 그다음 Priming 앱 로그인 화면을 바꾼다(앱이 먼저 바뀌면 「이용 신청하기」가 없는 화면으로 간다).
