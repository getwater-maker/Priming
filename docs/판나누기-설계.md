> 상태: **설계 확정(로이 승인 2026-11-05) · v1.0.26 장치 · v1.0.35 첫 승격 · v1.0.38 저장소 분리(로이 2026-11-05 「분리 + 한 방향 복사」).** 로이 결정 = 판매판은 롱폼만 · 회원 TTS = 클라우드 + 회원 PC 설치 · 판매판 승격은 로이 명령으로만.
> 🔴 **코드는 로이판(`D:\Priming` · 저장소 `getwater-maker/Priming`)에서만 고친다.** 판매판(`D:\Priming-Member` · 비공개 저장소 `getwater-maker/Priming-Member`)은 「판매판 올려」 때 로이판에서 **한 방향으로 복사**된다.
> 서버 쪽 약속 = [`요청서_wise-priming-판별업데이트.md`](요청서_wise-priming-판별업데이트.md) 덧붙임 2 · 회원제 전체 = [`회원제-설계.md`](회원제-설계.md).

## 배경

지금 Priming은 저장소 하나, 매니페스트 하나로 운영된다. 로이가 커밋을 푸시하면 로이 PC, 아내 PC, **회원 PC가 모두 같은 순간에 같은 코드를 받는다.** 조사해서 확인한 사실은 다음과 같다.

- **회원을 가르는 장치는 런타임 `isOwner()` 하나뿐이다.** main.js 12곳과 App.jsx 몇 곳에서 쓰고, 빌드 단계에서 기능을 끄는 플래그는 없다.
- **회원 설치본에도 열려 있는 로이 전용 기능이 있다.**
  - 2.0 무인제작(`--order`): 관문이 없고, 기본 폴더가 `D:\## 아도나이로이 2.0`이다.
  - 로이은행
  - 출판·부크크 자동 입력·Gmail 회신
  - 리모션
  - 화이트보드
  - 썸네일 편집기
  - OmniVoice 서버 연결
- **내부 문서도 회원 PC로 내려간다.** 매니페스트에 `docs/`가 들어 있어 회원제 설계(마진·Supabase 주소), 요청서, 작업노트, CLAUDE.md까지 받는다.
- **asar가 꺼져 있다.** 회원이 파일을 직접 고칠 수 있으므로 런타임으로 숨기기만 해서는 막을 수 없다.

로이가 정한 방향(2026-11-05):
- 판매판은 **롱폼만** 제공한다.
- 회원 TTS는 **클라우드와 회원 PC에 설치하는 TTS 모델**을 함께 쓴다.
- 판매판으로 넘기는 일은 **로이가 명령할 때만** 한다.

## 큰 틀 — 코드는 하나, 저장소·폴더는 둘 (v1.0.38 · 한 방향 복사)

> 📜 바뀐 경위: 처음(v1.0.26)엔 「저장소 하나 + 판매판 매니페스트(`update-manifest.member.json`, `ref` 고정) + Worker 가 **계정**으로 판을 고름」이었다.
> 2026-11-05 로이가 바탕화면 판매판에 **관리자 계정**으로 로그인하자 Worker 가 로이판 매니페스트를 줬고, 앱의 안전장치(다른 판 적용 금지)가 거절해 업데이트가 막혔다.
> → 로이 결정: **관리자용과 회원용을 GitHub 에 따로 올리고, 이 PC 에서도 따로 폴더·따로 세션으로 운영한다 — 단 코드는 로이판에서만 고치고 판매판은 복사만(「분리 + 한 방향 복사」).**

| | 🏠 로이판 | 🛒 판매판 |
|---|---|---|
| 폴더 | `D:\Priming` | `D:\Priming-Member` |
| 저장소 | `getwater-maker/Priming`(지금 그대로) | `getwater-maker/Priming-Member`(**비공개**) |
| 고치기 | ✅ **여기서만** | ⛔ 고치지 않는다(복사 때 덮인다 · 폴더의 CLAUDE.md 가 이 사실을 적는다) |
| 세션 | 코드·발행 | 판매판 시험·발행 확인·회원 대응(고칠 것은 로이판 세션에 요청서) |
| 매니페스트 | `update-manifest.json`(커밋마다) | 판매판 저장소의 `update-manifest.json` 하나(`edition:"member"` · `source` = 복사한 로이판 커밋 · `ref` 고정 없음 — 저장소 자체가 승격본) |
| 설치본 | `Priming-Studio-Setup-<ver>.exe`(로이판 저장소 Release) | `Priming-Setup-<ver>.exe`(**판매판 저장소** Release `member-v<ver>`) |

- ⛔ **두 벌로 고치지 않는다**(이 저장소의 단골 사고 = 「같은 일을 하는 코드가 여러 곳」). 무엇을 판매판에 넣을지는 지금처럼 `core/edition` 의 `FEATURES`·`MEMBER_DROP` 한 곳이 정하고, 복사 스크립트는 `gen-manifest --edition member` 의 목록을 그대로 쓴다.
- 복사는 **한 방향뿐**이다 — 로이판 → 판매판. 판매판 폴더에서 고친 것은 다음 복사 때 사라진다.

| 축 | 🏠 로이판 (Studio) | 🛒 판매판 (Member) |
|---|---|---|
| **무엇이 들어 있나** | 전부 | 롱폼 기능 + 회원 필수 기능. **로이 전용 파일은 아예 넣지 않는다**(숨기는 게 아니라 뺀다) |
| **언제 받나** | 지금처럼 `main`에 푸시할 때마다 | 로이가 「판매판 올려」라고 한 커밋만. 그때 판매판 저장소에 복사·푸시된다 |
| **누가 받나** | 관리자 계정(`admin`). 로이 PC와 아내 PC | 일반 회원 |
| **헤더 표시** | `Priming Studio v1.0.x` | `Priming v1.x` |

### ① 기능 표를 한 곳에 — `core/edition.js` (새로 만듦)
- `EDITION`은 설치본의 `edition.json`(빌드가 씀)에서 읽는다. 값은 `studio` 또는 `member`이다. 파일이 없으면 `studio`이다(개발 실행·E2E는 지금처럼 전부 열림).
- `FEATURES` 표 하나에 기능 id, 들어가는 판, 그 기능에 딸린 파일 목록을 적는다. 예시: `order`, `book`, `remotion`, `whiteboard`, `thumbEdit`, `royBank`, `ytCookie`, `localQwen`, `gpuTemp`, `monitorOff`, `todayScripts`, `omniServer`. (옛 `legacyEngines` 는 v1.0.49 에 그 코드를 저장소에서 지우며 뺐다)
- 판정은 `feat(id)` 하나다. 결과는 판(edition)과 관리자 여부(`isOwner()`)를 함께 본 값이다. 지금 흩어진 `isOwner()` 12곳은 `feat('…')`로 바꾼다. `isOwner()`는 남겨 두고, 관리자 계정 판정에만 쓴다.
- 렌더러는 `licPublic()`에 `features`를 실어 받는다. 화면은 `owner` 대신 `feat` 값으로 모드 탭, 리본 단추, 로그 상자 탭, 설정 탭을 가른다.
- 판매판에서 빠진 모듈이 있다. main은 이 모듈을 **필요할 때만 `require`하고, 없어도 넘어가야 한다**(`optionalRequire`). 해당 IPC는 「이 판에는 없는 기능」을 돌려준다.

### ② 판매판 폴더·저장소·설치본 — 파일을 실제로 뺀다 (v1.0.38 개정)
- `scripts/gen-manifest.js --edition member --out <파일>`이 `FEATURES`의 로이 전용 파일과 내부 문서를 뺀 목록을 만든다(`--out` 필수 — ⛔ 로이판 저장소에 판매판 매니페스트를 쓰지 않는다).
- 회원 PC로 보내지 않는 문서는 `docs/` 전체, `CLAUDE.md`, `AGENTS.md`, `test/`, `tools/`이다. 단 앱이 화면에서 쓰는 `docs/대본-작성-가이드.md`는 보낸다.
- **한 방향 복사** `scripts/export-member.js [--to D:\Priming-Member] [--dry]`(`npm run export:member`):
  - 위 목록대로 판매판 폴더를 **똑같이** 맞춘다 — 없는 파일 복사 · 다른 파일 덮어쓰기 · 목록에 없는 파일 지우기(`.git`·`node_modules`·`dist` 와 고유 파일만 남김).
  - 고유 파일: `update-manifest.json`(판매판 매니페스트) · `CLAUDE.md`(원본 = 로이판 `docs/판매판-폴더-CLAUDE.md`) · `edition.json`(member — 그 폴더에서 켜면 판매판) · `.gitignore` · `.gitattributes`.
  - 판매판 버전이 거꾸로 가면 멈춘다(`ALLOW_VERSION_DOWNGRADE=1` 로만 우회).
- `npm run dist:member`는 같은 목록으로 설치본을 만든다(electron-builder · `edition.json=member` · publish 대상 = 판매판 저장소). 출력은 `Priming-Setup-<ver>.exe`. 로이판 설치본은 `Priming-Studio-Setup`.
- **승격 명령** `npm run release:member -- --confirm [--installer]`(로이판 폴더에서 · 로이가 「판매판 올려」라고 할 때만):
  1. 로이판 작업 트리 깨끗 · main · `test:edition --no-e2e`
  2. `update:publish` → 바뀐 것 없음(판매판은 이미 푸시된 로이판 커밋에서만 나간다)
  3. `export-member` → `D:\Priming-Member`
  4. `test:edition --dir D:\Priming-Member`(금지 파일·문자열 0 · 매니페스트와 폴더 일치 · 그 폴더 파일만으로 켜기 · 롱폼 무음 만들기)
  5. 판매판 저장소 커밋(`release: 판매판 v<ver> (로이판 <sha>)`) · 태그 `member-v<ver>` · 푸시
  6. `--installer`: `dist:member` → 판매판 저장소 Release `member-v<ver>` 에 `Priming-Setup-<ver>.exe`(의존성이 바뀐 승격·판 경로가 바뀐 판에 필요)
- 처음 한 번(로이 확인 뒤): `gh repo create getwater-maker/Priming-Member --private` → `D:\Priming-Member` 에서 `git init -b main` · `git remote add origin …` → 첫 `release:member`.

### ③ 업데이트 길 — Worker 가 **판(edition)으로 저장소를 고른다** (v1.0.38 개정 · wise-priming 요청서 덧붙임 2)
- 앱은 매니페스트·파일 주소 **둘 다**에 `edition=<이 설치본의 판>` 을 싣는다(`core/license` 의 주소 만들기 한 곳 · light-updater 는 판만 넘긴다).
- Worker:
  - `edition=member` → **판매판 저장소**(`Priming-Member` · `main` · `update-manifest.json` · 파일은 그 매니페스트에 있는 것만). 받는 사람 = 유효 회원 · 관리자 · **로그인 전 · 회원 아님 모두**(로이 2026-11-05).
  - `edition=studio`(또는 없음) → 관리자면 로이판 저장소(`Priming` · 지금 그대로) · 관리자 아니면 판매판(옛 회원 설치본이 판매판으로 바뀌는 길 — 앱은 토큰으로 물은 때만 받아들인다).
  - 이 규칙이 「판매판에 관리자로 로그인 → 로이판이 와서 업데이트가 막힘」(2026-11-05)을 없앤다.
- 앱 안전장치는 그대로: 판매판 설치본은 판매판 매니페스트만 적용 · 토큰 없이 온 판매판은 로이판 설치본에 적용 ⛔(`light-updater.editionGate`).
- 「전부 받아 해시 확인 → 그 뒤에만 교체」, deps 해시, 역행 방지는 그대로 둔다(`test:updater`).
- 판매판 버전은 로이판과 같은 번호 줄을 쓴다(승격된 커밋의 번호 · 건너뛸 수 있다).
- 🔴 **순서**: ① 판매판 저장소 만들기·첫 푸시 → ② Worker 판 분기 배포(그 전엔 판매판 저장소가 비어 있으면 회원에게 `no_member_release`) → ③ 판매판 설치본 새로 깔기(바탕화면 판매판 1.0.28 은 새 주소를 모른다 — 덮어 설치) → ④ 로이판 저장소의 옛 `update-manifest.member.json` 지우기 → ⑤ 로이판 저장소 비공개(맨 마지막 · 회원제 설계 §0).

### ④ 로이 PC 두 대

### ⑤ 금지 검사 — `test:edition` (새로 만듦)
- 판매판 매니페스트에 `FEATURES`의 로이 전용 파일과 `docs/`가 0개여야 한다. `--dir <판매판 폴더>` 면 그 폴더의 `update-manifest.json` 과 폴더 파일이 똑같은지(빠진·다른·엉뚱한 파일 0)까지 본다(v1.0.38).
- 판매판 파일 전체에서 금지 문자열이 0건이어야 한다. 대상은 `D:\## 아도나이로이`, `D:\TTS_Model`, `D:\## 출판`, `로이은행`, `adonairoy`, `kie.ai/billing`이다.
- 빠진 모듈이 있어도 앱이 켜져야 한다. 확인 방법: 판매판 파일만 임시 폴더에 복사 → E2E 실행 → 롱폼 무음 만들기(`test:makeall` 판매판 변형).
- 판별력도 검증한다. 금지 파일을 일부러 넣으면 실패해야 한다.

## 작업 순서 (구현은 로이의 「진행해」 뒤에)

1. **설계 문서 저장**: 이 내용을 `docs/판나누기-설계.md`로 저장하고, CLAUDE.md §2에 규칙 한 줄을 넣는다. 규칙 내용: 「새 기능은 로이판에 먼저 넣고, 판매판은 승격 때만 받는다. 로이 전용 기능은 `FEATURES`에 등록한다.」
2. **wise-priming 요청서**: Worker 판 분기. 서버 세션이 먼저 해야 한다.
3. **`core/edition` + `feat()`**: `isOwner()` 12곳과 화면 `owner` 분기를 이쪽으로 옮긴다. 모드 탭(출판·리모션)과 화이트보드 항목도 숨긴다. 로이판 동작은 바뀌지 않아야 한다.
4. **빠지는 모듈의 지연 `require` 정리**: 판매판 파일 묶음만으로 앱이 켜져야 한다. 2.0 무인제작은 bootstrap 입구에서 판을 확인한다.
5. **판매판 매니페스트·설치본·승격 명령** + `test:edition`
6. **판매판 추가 기능**: A4 첫 실행 → A5 기본값 → A3 클라우드 TTS → A2 PC 설치(라이선스 확인 뒤) → A6 대행(서버 준비 뒤)
7. **첫 승격**: 로이 PC에서 판매판 설치본으로 따로 시험 → `release:member` → 그 뒤 저장소 비공개 전환(회원제 설계 §0)

1~5는 한 줄로 이어지는 하나의 변경이다(같은 파일, 서로 결과가 필요함). 6의 각 항목은 따로 진행할 수 있다.
